# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

"Cephalon Ordis", the Discord bot for the Warframe clan "The Rats Den 69" (TypeScript, ESM, Node 24, discord.js v14). It also serves an MCP server over HTTP and is published as a Docker image (`flavio11113/rats-den-warframe-bot`) to Docker Hub by GitHub Actions.

**Identity:** `src/discord/identity.ts` syncs the bot's Discord username (`BOT_NAME`) and avatar (`assets/clan-logo.png`, which the Dockerfile copies into the image) on every `ClientReady`. It only calls the API when something differs, because Discord rate-limits both; the avatar hash is kept in the `bot_meta` table. Embeds use `brandIcon(ctx)` (the bot's avatar URL) for icons, and `COLORS.brand` is the crystal blue sampled from the logo.

## Commands

```bash
npm run dev          # tsx watch, loads .env (copy .env.example first)
npm run typecheck    # tsc --noEmit over src + test
npm test             # node:test via tsx, all test/**/*.test.ts
npx tsx --test test/db.test.ts                         # one file
npx tsx --test --test-name-pattern="markSeen" test/db.test.ts   # one test
npm run build        # tsc -p tsconfig.build.json → dist/
npm start            # node dist/index.js
```

TypeScript is v7 (native `tsc`). Relative imports must use `.js` extensions (NodeNext resolution).

## Architecture

`src/index.ts` builds one `AppContext` (`config`, `store`, discord `client`, see `src/context.ts`) and hands it to three consumers that run in the same process:

1. **Discord interactions** (`src/discord/bot.ts`): routes slash commands (`src/discord/commands/*`, each exporting a `Command`), autocomplete, and buttons (`src/discord/buttons.ts`). Commands are registered **guild-scoped** to `DISCORD_GUILD_ID` on every `ClientReady`; the bot deliberately serves only that one guild. Button custom IDs are `rsvp:<eventId>:<going|maybe|declined>` and `lfg:<postId>:<join|leave|close>`, so they keep working after restarts.
2. **Notifier** (`src/discord/notifier.ts`): wakes every minute (event reminders) and uses the worldstate, which is fetched at most every `WORLDSTATE_POLL_SECONDS`. `collectAlerts()` is a pure function that returns every currently alert-worthy item with a stable `key`; `Store.markSeen(key)` de-duplicates across restarts. On an empty `seen_worldstate` table it records the current items without posting (no flood on first deploy). It also sends event reminders 15 minutes before start. **The alerts channel holds ONE live summary message** (`src/discord/summary.ts`, `updateSummaryMessage` in `notifier.ts`): a single embed with cycles, fissure counts by tier, the sortie, Archon Hunt, the Arbitration (only while one runs; it is read from the feed's `arbitration` entry, which is an expired placeholder when none does, and it never pings), Baro, Steel Path honors, alerts and the invasions worth running (`summaryEmbed` is pure and drops a malformed section instead of the message), edited in place when its content fingerprint changes (at most every 2 min, at once when something new appeared; the stale note carries no minutes, so it doesn't change every minute), reposted if someone deletes it (Discord error 10008), and remembered across restarts in `bot_meta` `alerts_summary:<channelId>` (message id, hash, time). When `collectAlerts` finds something new (and it is not the first run on an empty `seen_worldstate`) a separate short message lists the new titles, pings `alertsRoleId` and links the summary; there are no longer separate alert embeds. Only alerts with a `NOTABLE_REWARD` are announced (an event's endless "Event Alert Title" resource missions every 30 min are only listed in the summary, named by `alertName()` as "Event mission (Survival)"), and that note is replaced by the next one (`postNote`, id in `bot_meta` `alerts_note:<channelId>`) and removed after 3 h (`expireNote`), so the channel holds the summary plus at most one note. `test/alerts-summary.test.ts`.
3. **HTTP server** (`src/http.ts`): the public status page `/` plus `/status.json` and `/logo.png` (`src/web/status.ts`). The page is a headline strip (next cycle change, Baro, Arbitration, sortie, fissures) above four sections (Open worlds, The Void, Resets, Events and trading) of tiles in a CSS grid; the Void fissures tile lists every open fissure with Steel Path/Storm/tier filter chips (client-side, kept in sessionStorage), alerts come from `foldAlerts` (shared with the Discord summary), and the inline script ticks the countdowns every second and re-fetches `/` every minute to swap in the new `<main>` without a reload (the CSP has `connect-src 'self'` for that). `worldOf()` builds each tile's data inside its own try/catch, so one malformed worldstate section can't blank the page. The page and its JSON are server-rendered with no build step; the page's inline style and script are allowed by a per-request CSP nonce, and every dynamic string goes through `escapeHtml`. `buildStatus` reads only cached Discord data and exposes aggregates, never member names or IDs. There's also `/health` (no auth, used by the Docker HEALTHCHECK) and, only when `MCP_AUTH_TOKEN` is set, `POST /mcp`. Express 5 reports listen errors through the `app.listen` callback, and the bot exits on them. MCP is **stateless Streamable HTTP**: a new `McpServer` (`src/mcp/server.ts`) and transport are built per request, so `createMcpServer` must not do I/O. Bearer auth runs before body parsing; `MCP_ALLOWED_HOSTS` adds DNS-rebinding Host checks.

**Free chat answers** (`src/answers/`): the default when there's no `ANTHROPIC_API_KEY`, and what the deployed bot uses (the owner won't pay for an AI API). `detectIntent()` in `intent.ts` is pure regex/keyword rules mapping a message to a lookup (price, drops, relic, world view, fissures, bounties, clan events, build, item, wiki fallback). Rule order matters: price before relic, and drops before world views. `test/intent.test.ts` pins real phrasings, so add a case when changing a rule. `smart.ts` turns an intent into an Ordis line plus an existing embed, and falls back to `searchWiki`, which prefers a page whose title appears in the question. `found: false` lets the chat channel stay silent. In the `/setup chat` channel Ordis answers anything written there, no question mark needed (`chat.ts`; `isChannelQuestion()` in `intent.ts` is no longer used for it): he skips messages with no text, a reply to another member's message (a conversation between members) and anything while he has nothing to say is no longer silent either, a lookup with no result still gets the "found nothing" reply. `src/discord/chat-topic.ts` keeps the channel's description (`CHAT_TOPIC`) in line with this: `syncChatTopic` runs at ClientReady and after `/setup chat`, the panel's Settings page and `update_bot_settings`, writes only when the topic differs and only with `ENABLE_MESSAGE_CONTENT` on, and needs Manage Channels (a failure just logs).

**Local model (Ollama)** (`src/answers/compose.ts`): `LOCAL_AI_URL` + `LOCAL_AI_MODEL` (+ optional `LOCAL_AI_KEY`, `LOCAL_AI_TIMEOUT_SECONDS` default 60) point `composeAnswer` at a self-hosted OpenAI-compatible server (Ollama `/v1`, reached over Tailscale or a tunnel). It is tried before the free cloud endpoint, has no daily limit, and a failure or timeout skips it for `LOCAL_COOLDOWN_MS` (3 min) so a sleeping host doesn't slow every question; a clean answer, including NOT_COVERED, is final. Only the free chat answers use it (not the screenshot vision fallback, which still needs `FREE_AI_KEY`). New vars follow the usual rule: config.ts, .env.example, compose, Portainer YAML.

**`/ai` command** (`src/discord/commands/ai.ts`, Manage Server): `/ai status`, `/ai tune`, `/ai model name:` (autocomplete from Ollama's installed models; `-` returns to `LOCAL_AI_MODEL`) and `/ai install tag:` (background download, one at a time, posts in the channel when done). The choice is kept in `bot_meta` (`local_ai_model`), loaded at startup, and wins over `LOCAL_AI_MODEL` everywhere through `localModelOf` (`src/ai/ollama.ts`, which also holds the Ollama API helpers shared with the MCP tools). **Ollama stack and MCP tools:** `docker-compose.ollama.yml` is a separate stack for the machine with the RAM (tailscale sidecar, ollama with one parallel slot, 4096 context, flash attention and an 8-bit KV cache, a one-shot `pull-model`, and a one-shot `tune-model` that creates `ordis-tuned` with `num_thread` (6 for the i9-13900HK performance cores, `OLLAMA_THREADS`) and `num_ctx`; select it with `/ai model`); the bot reaches it over the tailnet. With `LOCAL_AI_URL` set, `src/mcp/ollama.ts` registers `ollama_status` (reachable, installed and loaded models, background download progress), `ollama_pull` (background download, one at a time), `ollama_test` (timed answer) and `ollama_tune`, using Ollama's native API at the URL without `/v1`. **Tuning without shell access:** `tuneModel` (`src/ai/control.ts`, over `createVariant` in `ollama.ts` = `POST /api/create` with `from` + `parameters`, no download) makes `ordis-t<threads>` (default context 4096) as a copy of the model in use; `/ai tune threads: [name] [context] [use]`, `ollama_tune` and the AI page's tuning form all call it, so thread counts (6/8/12 on a 13900HK) can be compared with `/ai test` without touching the host.

**AI switches and control** (`src/ai/settings.ts`, `src/ai/control.ts`): six runtime switches (`local`, `thinking`, `websearch`, `operators`, `log`, `cache`; defaults on/off/on/on/on/on) kept in memory and in `bot_meta` (`ai_toggle_<name>`, loaded in `index.ts`). `compose.ts`, `vision.ts`, `websearch.ts`, `operator.ts` and `log.ts` read them with `aiToggle()`. Thinking sends `reasoning_effort:'low'` (and 3000 max tokens) only when `modelCapabilities()` (Ollama `/api/show`, cached 10 min) lists `thinking`: a model without it (the E4B) gets HTTP 400 for anything but `'none'`, so it is never sent. `control.ts` holds every action (`aiOverview`, `chooseModel`, `installModel`, `setToggle`, `testModel`) and is the only thing the `/ai` command (`status|model|install|toggle|test`), the admin panel's **AI** page (`src/web/admin/ai-page.ts`: status, switches, model, download, test, recent questions) and the MCP tools (`set_ai_switch`, `choose_ai_model`, `get_bot_health.ai.switches`) call, so the three surfaces always show and change the same state. `test/ai-toggles.test.ts`.

**Agent and brain** (`src/agent/`; **retrieval first**: `prefetch.ts` `wikiPrefetch` searches the wiki with the member's own words before the model runs (brain setting `retrieveFirst`, default on; skipped for follow-ups, tiny questions, live questions (price, world state, fissures, bounties, clan events: the live-data tool answers those and generic wiki text would tempt the model to skip it) and without the `search_wiki` tool; 8 s limit, never fails a run) and appends up to 3 passages (900 chars each) to the user message as data, titles kept in `run.prefetched`, because a small model turned "endo" into a search for "Arcane Energize"; `test/prefetch.test.ts`; the agent waits at least `AGENT_LOCAL_MIN_TIMEOUT_SECONDS` (150) per local request whatever `LOCAL_AI_TIMEOUT_SECONDS` says, because a step reads the whole prompt and tool results and a 60 s limit made the 26B and even the E4B time out with prefetched passages; defaults tuned for a small model: temperature 0.25, Ordis-ness 10, a "which tool for what" guide, grounding rules and keyword-search advice in `DEFAULT_PROMPT`): a tool-using agent for open-ended questions, written as a plain loop over any OpenAI-compatible endpoint (local Ollama first, then the free cloud model, like every other answer). `run.ts` `runAgent()` gives the model the system prompt, the question and the enabled tools; the model decides which to call, how often and when to stop; results go back to it until it answers, and the last step has no tools so it must answer (identical calls are served from a per-run cache, at most 4 calls per step, 25 s per tool, 4 min overall). Tool calling is native (`tools` in the request) when Ollama reports the `tools` capability (`modelCapabilities`), otherwise the loop tells the model to write `<tool_call>{json}</tool_call>` and parses it; a 400 "does not support tools" retries in text mode. `tools.ts` is the provider-neutral registry (worldstate, fissures, lookup_item, search_drops, price_check, search_wiki, read_wiki_page, search_web (SearXNG, only when `SEARXNG_URL` is set and the Web search switch is on), get_clan_info); errors go back to the model as `{"error":...}`. `brain.ts` is the tuning document (one JSON in `bot_meta` `brain_settings`, clamped by `normalizeBrain`, loaded in `index.ts`): editable system prompt (placeholders `{{bot}} {{clan}} {{date}} {{persona}}`; empty = `DEFAULT_PROMPT`), **Ordis-ness** 0-100 (`PERSONA_BANDS`: Off, Hint, Light, Strong, Full; `toneFor()` gives the single-shot writers `compose.ts` and `operator.ts` plain tone up to 25 and the persona text above, and below 10 the canned intro lines in `smart.ts` become neutral), temperature, top_p, max steps, tokens, answer and tool-result limits, who gets the agent (`agentFor` off/operators/everyone, default operators), scope (`open` = wiki/build intents, `all` = everything but help; prices, drops and world state keep their exact embed answers unless scope is `all`), tool mode, show-tools footer and the per-tool off list. `smartAnswer` tries `useAgent` first, then the old operator answer, then the plain lookup. The operators' extra paragraph (`OPERATOR_NOTE`, same hard limit as before) is added by the code for `OPERATOR_IDS` only. `traces.ts` keeps the last 30 runs in memory (every model call, exposed reasoning, tool calls with arguments and results) for the panel. Surfaces: the admin panel's **Brain** page (`src/web/admin/brain-page.ts`: persona slider, prompt editor, tuning, tool checkboxes, the assembled prompt, a playground that runs in the background and refreshes itself, and the run traces), `/ai persona level:` and the MCP tools `get_brain`, `update_brain`, `test_agent` (`src/mcp/brain.ts`). `test/agent.test.ts`.

**Answer cache and daily refresh** (`src/answers/cache.ts`, table `answer_cache`, migration 20): repeat questions get the same, checked answer instead of a fresh model answer. **Reading:** `smartAnswer` looks the question up by `normalizeQuestion` (lower-case, no punctuation; exact match only) before the agent/operator/lookup paths, for non-operators and not for live intents (`cacheAllowedFor`: price, world, fissures, bounties, clanEvents, help), and serves a verified answer up to 14 days after it was refreshed (`source: 'cache'` in the AI log, wiki sources rebuilt for the embed, no model call). `cacheable()` refuses anything that smells live (now, today, latest, update, Baro, fissures, prices, events, clan...). **Writing happens only in the daily job** (`AnswerRefresher`, once a day at `ANSWER_REFRESH_HOUR_UTC`, the day recorded in `bot_meta` first so a crash loop can't repeat it; `ANSWER_REFRESH_ENABLED=false` or the `Answer cache` switch turns it off): `pickCandidates` takes questions from `ai_log` (30 days) that a model or plain excerpt answered, asked 2+ times, not operator or live, never more than `ANSWER_REFRESH_MAX` (8) per run, most asked first, skipping saved answers younger than 7 days or not asked for 14, and backing off after failures (1 day, then 7 after 3). `researchAnswer` runs the agent with an instruction to say exactly how something is obtained, then rejects unless research really used wiki/item/drop/web tools with a non-error result and no live-data tool (`quickCheck` also rejects hedging and a "where/how do I get X" answer that never says how), and finally a judge call (`composeWith`) compares the answer with the tool results and must reply PASS. Only then `saveCachedAnswer`; a failure keeps the previous answer and bumps `fails` (a row without an answer is never served). Old rows are pruned after 45 days. `/ai cache action:status|refresh`, the AI page's **Answer cache** section (list, Forget, Refresh now) and the last run's summary (`bot_meta` `answer_refresh_last`) operate it. The local model's compose request also sends `seed: 7`, so identical excerpts give identical wording. `test/answer-cache.test.ts`. New env vars have defaults, so the Portainer YAML needs no change.

**Thinking notice** (`src/discord/progress.ts`, `src/answers/status.ts`): a slow free answer in chat, DMs or `/ask` shows a message with a progress bar (fills over ~60 s), the seconds spent and the current step ("Searching the wiki", "Reading a wiki page", "Thinking (step 2)"...), edited every 4 s, so users can tell the bot is working; it only appears after 2.5 s, so quick and cached answers never show it. `startProgress(post)` returns `set/finish/stop/discard`; chat deletes the notice and then replies (so the reply still pings), `/ask` edits it into the answer. Steps report through `reportStatus()` (an AsyncLocalStorage listener scoped by `smartAnswer`'s optional `onStatus`), so nothing in between passes callbacks; the agent reports tool calls via `onEvent` with `stream:false`, so Discord answers keep using plain requests. A failing notice never stops an answer. `test/progress.test.ts`.

**Queues** (`src/queue.ts`, `src/answers/slot.ts`; Config page group "Queues": `QUEUE_QUESTIONS_CONCURRENCY`, `QUEUE_SCREENSHOTS_CONCURRENCY` (default 1 each, so a CPU model works on one thing at a time), `QUEUE_MAX_WAITING` (20); one person may have 2 running or waiting per queue): `WorkQueue` is an in-memory FIFO with `join(key, onPosition)` returning a ticket (`position()`, `ready`, `release()`; a stuck job is released after 6 min; `QueueFullError` when the person or the line is full). **Questions:** only the model steps wait (`withModelSlot` around `agentAnswer`, `operatorAnswer` and the wiki `composeDetailed` in `smart.ts`, and each research in the daily answer refresh); price, drop, world state and clan lookups and cached answers are never queued. The asker travels in an AsyncLocalStorage (`withAsker`), the position goes out through `reportQueue` to the `StatusListener.queue` of the answer, and `startProgress`'s `listener` (pass `progress.listener` to `smartAnswer`) turns that into the same Discord message: at once (no 2.5 s delay) "Ordis is busy with other questions, you're #N in the queue", edited as the line moves, and when the turn comes (position 0) it becomes the normal "Ordis is thinking" message with its clock starting then. Too many waiting gives a plain reply (intent 'busy', not logged as an answer source). **Screenshots:** `handleSsMessage` joins `screenshotQueue` first, REPLIES to the member's message with the queue message (or the usual "Reading your screenshot") and downloads the picture, then waits for its turn before reading; the 90 s limit only counts the reading. `get_bot_health.queues` and the Config page show the queue state. `test/queue.test.ts`.

**AI question log** (`src/answers/log.ts`, `/ailog`, table `ai_log`): every free answer given in the chat channel, in DMs or by `/ask` is recorded with asker, channel, question, intent, source (`local` Ollama, `cloud`, `excerpt`, `lookup`), model, milliseconds and the start of the answer, and pruned after 30 days. `smartAnswer` fills `source/model/intent/ms` (via `composeDetailed`, which says which endpoint wrote the text); `logAnswer` never throws. `/ailog [count] [member]` (Manage Messages) shows the newest entries plus the last 24 h per source. The Claude (`ctx.ai`) path is not logged.

**Corrections and conversation memory** (`src/answers/corrections.ts`, `src/discord/corrections.ts`, `src/answers/memory.ts`, the panel's **Corrections** page `src/web/admin/corrections-page.ts`, tables `corrections` and the new `ai_log` columns `message_id`/`rating`, migration 24): every answer Ordis posts is logged with its Discord message id (`logAnswer(..., messageId)` returns the log id), so a reply to it can be matched back (`store.aiLogByMessage`). **Correcting:** `handleCorrectionReply` runs in `handleChatMessage` before the "is this a question" filter: a reply to a logged answer that does not end in `?` (and is not thanks or under 12 characters) is a correction. From staff (`isStaff`: `OPERATOR_IDS`, `PANEL_OWNER_IDS`, panel admins, or anyone with Manage Server) it is saved `approved` at once (✅); from anyone else it is `pending` (📝) until staff approve, edit or reject it on the Corrections page. A reply ending in `?` is a follow-up question, and any reply to an answer is picked up in the chat channel without needing `?`. Approving drops the saved cache row for that question and marks the logged answer wrong. **Using them:** `smartAnswerInner` first serves `findCorrection` (approved, exact `normalizeQuestion` match, newest wins) word for word as `source: 'correction'`, before the cache, agent or lookups; for related questions `guidanceFor` (keyword overlap `relatedness` >= 0.6, max 4 corrections plus 2 answers rated wrong and 2 rated right, capped at 2400 chars) is added to the agent's system prompt (`AgentDeps.guidance`) and to the operator and wiki writers (`extra`). Only approved text and staff-rated answers ever reach a prompt; pending suggestions never do. Rated log rows are kept past the 30-day prune. **Reactions** (`src/discord/ratings.ts`): chat and `/ask` answers that were logged (not DMs, staff corrections or queue notices) get ✅ and ❌ added by the bot; `handleRatingReaction` (`MessageReactionAdd`/`Remove`, intent `GuildMessageReactions`, partial `Reaction`) lets staff (`isStaff`) set or clear the same `rating` the panel buttons set, and ignores everyone else. The bot needs Add Reactions and Read Message History in the channel. The panel page also adds corrections by hand, rates recent answers right/wrong and writes the right answer under one. **Memory:** `memory.ts` keeps the last messages of one person in one channel (`memoryKey(channelId, userId)`, DMs separate) in memory only, forgotten after 30 minutes idle and on restart; `smartAnswer` takes `asker.key` (chat, DMs and `/ask` pass it), replays `brain().memoryMessages` (Brain page slider, default 10, 0-30, 0 = off; one message is one side of an exchange) as real chat messages to the agent and as a transcript to the single-shot writers. A short message that points back (`isFollowUp`: pronouns, "and", "what about"...) goes to the agent for everyone and every intent (`useAgent(..., followUp)`), skipping the correction match and the answer cache, which only know the question text. `test/corrections-memory.test.ts`, plus panel tests in `test/admin.test.ts`.

**Editing the bot's messages** (`src/discord/messages.ts`): `editOwnMessage` / `ownMessages` are the one implementation behind the MCP tool `edit_message` (channel_id, message_id, content; find the id with `read_messages`, `bot: true`) and the admin panel's **Messages** page (`src/web/admin/messages-page.ts`, under Server: pick a channel, edit the text of each message Ordis wrote there, audit-logged, returns to the same channel). Discord only lets a bot edit its own messages, so anyone else's are refused (and not offered in the panel); embeds are kept, text is limited to 2000 characters, mentions never ping. `test/messages.test.ts` and a panel test in `test/admin.test.ts`.

**Event end times** (`events.ends_at`/`ended`, migration 25): an event may have an optional end. `/event create ends:`, the panel's Events form (UTC datetime) and the MCP `create_event` `ends_at` take a length after the start ("2h", `parseEnd` in `time.ts`) or a time; it must be after the start and at most 30 days later (`createClanEvent`). `renderEvent`/`whenText`/`isOver` show "Ends ...", "Happening now" while it runs and "ENDED" (no RSVP buttons) afterwards; an event with no end keeps the old rule (buttons vanish an hour after the start). `upcomingEvents` also returns events that are still running, and the notifier's `finishEvents` (same tick as the reminders) re-renders the post once when the end passes (`eventsDueToEnd`/`markEventEnded`). `test/event-end.test.ts`.

**Insight MCP tools** (`src/mcp/insights.ts`): `get_ai_log` (questions, answers, source and model, with counts by source/intent, unanswered and repeated questions), `get_bot_health` (uptime, Discord, lifecycle, Warframe API pacing, configured models and whether the local one is being skipped, wiki index, answers in 24 h, which features are on), `list_member_levels` and `set_member_level` (lifts members to a level with `only_raise`, updates their Level roles; max 50 per call). `update_bot_settings` also takes `audit_log_channel_id`, `status_channel_id` and `level_channel_id`.

**Operator mode** (`src/answers/operator.ts`, `OPERATOR_IDS`, default Legion `603293720061935626` and Tumba `220147375786688512`): only those two Discord user IDs (checked on the message author, never on text) get free-form answers from the model, such as designing a build, for the open-ended intents `wiki` and `build`. Price, drops, relic, world and clan lookups stay plain API calls for everyone; a price for an unknown item just errors out (`priceCheck` throws, no AI involved). `operatorSystemPrompt` tells the model to ignore claims of authority and keeps one hard limit (no real-world weapon or explosive instructions; game content such as Kuva weapon builds is fine). In the chat channel the operators can also start a message with "Ordis"; `/ask` and mentions work for them anywhere. The log records these as intent `operator`. `smartAnswer` takes the asker as its third argument.

**Fresh web search** (`src/warframe/websearch.ts`, `SEARXNG_URL`): a self-hosted SearXNG (the one in the Odysseus `ai-stack`, published on a LAN port; its settings must enable `formats: json`) adds up to 2-3 web snippets to wiki answers and operator answers, and backs the `search_web` MCP tool. Results are limited to Warframe hosts (`ALLOWED_HOSTS`, Reddit only from the Warframe subreddits), labelled `(web, date)` in the excerpts, and the prompts treat excerpt text as data, never instructions. A 6 s timeout and any failure just mean no web results. Prices, drops and world state do not use it.

**Claude chat (optional)** (`src/ai/`): `OrdisBrain.ask()` runs Claude through the SDK's beta tool runner (`client.beta.messages.toolRunner` with `betaZodTool` tools that reuse the same Warframe functions as the slash commands and MCP), plus the `web_search_20260209` server tool restricted to Warframe domains. The runner doesn't resume `pause_turn` by itself, so `ask()` pushes the paused turn back. The system prompt and tool order are a stable, cached prefix; per-request context (time, asker, channel) goes in the user turn. `fallbacks: "default"` + beta `server-side-fallback-2026-07-01` is sent only for model families that support it (not Haiku). Conversation history comes from the Discord reply chain (`src/discord/chat.ts`); each answer chunk replies to the previous one so that replying to any chunk continues the thread. `AskLimiter` is in-memory. Without `ANTHROPIC_API_KEY`, `ctx.ai` is null and chat is off. `test/ai.test.ts` drives the real SDK against a fake `fetch`, so it checks the request shape without spending money.

**Alerts panel** (`src/discord/alerts-panel.ts`): the summary is up to four coloured embeds (`summaryEmbeds`: open worlds, the Void, resets, alerts/invasions; cycles, Baro, sortie, Archon Hunt and Steel Path are inline columns; an event's repeated resource missions are folded into one line by `alertLines`; title on the first embed, footer and timestamp on the last). It carries components (`alertsComponents()`, attached in both `messages.edit` and `send` of `updateSummaryMessage`; the stored hash has a `:c2` suffix, bump it when the layout or components change so the live message is edited once): buttons `alerts:fissures|sortie|archon|arbitration|baro` answer ephemerally with the existing embeds, `alerts:mine` lists the member's trackers, and the string-select menu `alerts:track` (routed in `bot.ts`, `handleAlertsSelect`) creates trackers from `TRACK_OPTIONS` (skips duplicates, respects `MAX_TRACKERS_PER_USER`). Each summary section ends with a short `-#` hint saying what it means. `test/alerts-panel.test.ts`.

**Trackers** (`src/trackers.ts`; kinds reward, fissure, cycle, baro, arbitration (optional mission type), sortie (optional mission), archon; `/track arbitration|sortie|archon`): `collectTrackables(ws)` turns the worldstate into keyed items (invasions, alerts, Darvo, events, Steel Path, Varzia, Baro, fissures, cycle phases) and `matchTracker(spec, item)` is pure. The notifier de-duplicates per tracker with `seen_worldstate` keys `track:<id>:<item key>` and sends one DM per member per poll.

**Wiki index** (`src/wiki/`): `crawler.ts` lists every main-namespace article with its latest revision (`generator=allpages&prop=info`, 500 per request), downloads only the changed ones as wikitext (40 per request, `prop=revisions&rvslots=main`), and removes deleted ones; it refuses to shrink the index below half its size (a truncated listing must not wipe it). `clean.ts` turns wikitext into plain text (nested template removal with a small allowlist of display-only templates, tables flattened to rows, links and markup stripped) and splits it into ≤1000-character chunks by heading. `index.ts` stores them in an FTS5 table (porter stemming) in its own `wiki.db`, deliberately outside `bot.db` so it never bloats backups or migrations. `search()` puts the page whose title appears in the question first (shell pages like `Kuva Lich` fall through to `Kuva Lich/Main`), then bm25 matches (all words, then most words); patch-note pages are excluded unless the question mentions updates. `searchWiki`/`readWikiPage` in `warframe/wiki.ts` consult the index first once it has 500+ pages, and fall back to the live API, so every consumer (chat, `/wiki`, MCP, Claude) benefits. **Meaning-based reranking** (`src/wiki/embed.ts`, `EMBED_MODEL` default `nomic-embed-text`, installed in the same Ollama with `/ai install tag:nomic-embed-text`; needs `LOCAL_AI_URL`; empty = off): `searchWiki` passes the full-text results plus up to 12 extra pages from a looser OR query (`WikiIndex.pool`) to `rerankPassages`, which embeds the question and the passages through Ollama's `/api/embed` (vectors cached in `wiki.db` table `embeddings`, keyed by a hash of model + text, pruned past 30,000) and blends the full-text position (45%) with the cosine similarity (55%); an extra page needs a similarity of 0.5 to get in, so a word-only match never replaces a real answer. Any failure (model not installed, Ollama down, timeout) returns the plain results and pauses the embedder for 5 minutes; `get_bot_health.wikiEmbeddings` shows its state. `bindEmbedder(config)` binds the shared config object, so a model changed on the Config page applies at once. `test/wiki-embed.test.ts`. The wiki's full-page extracts are limited to one page per request, which is why this reads wikitext instead.

**Third-party API client** (`src/warframe/fetch.ts`, `src/warframe/cycles.ts`): every outbound Warframe call goes through the one `ApiClient` (`api`; `apiFetch` for raw responses, `apiJson` for cached JSON with `kind: 'live' | 'price' | 'stable'`). It spaces requests per host (`API_MIN_INTERVAL_MS`), caps all hosts per minute (`API_RATE_LIMIT_PER_MINUTE`; background work such as the wiki crawler gets half and a queue longer than 10 s throws `ApiBusyError`), answers a 429 by leaving that host alone for its `Retry-After`, and a 403 by a cooldown (`API_COOLDOWN_MINUTES`) in which nothing is sent (`ApiBlockedError`, never retried). Server errors and timeouts retry `API_MAX_RETRIES` times with exponential backoff and jitter. `api.get` caches successful answers in memory and in the `api_cache` table (bot.db; prices `API_PRICE_CACHE_SECONDS`, items/drops/wiki `API_STABLE_CACHE_HOURS`), shares identical in-flight requests, revalidates with ETag / Last-Modified, and when the host can't be used returns the expired entry with `stale: true` (limited by age per kind) instead of failing; errors are never cached. The world state keeps its own pacing (`WORLDSTATE_POLL_SECONDS`, `retryAt` after a failure, conditional request against `<DATA_DIR>/worldstate.cache`); `worldStateStaleNote()` says when what is shown is outdated, and `projectCycles` rolls Cetus, Vallis, Earth, Cambion and Zariman (150 min Grineer/Corpus) forward from their fixed phase lengths so cycles are right between polls (embeds, MCP, status page, and the cycle trackers, whose key rounds the expiry to the minute so a calculated and a real expiry never notify twice; Duviri comes from the feed). `SOURCE_LAG_MS`: when the source's own `timestamp` was more than 20 min older than the moment it was fetched (warframestat.us lags at times), `worldStateStaleNote()` says so (cycles and fissures embeds, MCP `warning`) and the status pill shows "source data N min behind". Settings live in the Config page ("API limits and cache", plus an activity card); `get_bot_health` shows `apiClient` stats. `test/api-client.test.ts` uses a fake clock and fetch.

**Small guards** (each has a test): `src/imaging/size.ts` reads the size a PNG/JPEG/WebP header declares and refuses anything over 40 million pixels before a decoder allocates it (a 43 KB file can declare 6000x6000; `normalizeImage`, `decodeImage`, `decodeWebp` and `scanCard` all check); `src/timeout.ts` `withTimeout` races work against a limit and clears its timer (use it instead of a bare `Promise.race` with a `setTimeout`); `src/own.ts` `own(table, key)` looks a user-typed or model-chosen key up in a plain table without finding `constructor`/`toString`; `apiJson` only caches an answer that looks like JSON, so a Cloudflare HTML page sent with HTTP 200 is an error (stale data is served instead) and is never stored; the OCR stat-line pattern in `rivens/card.ts` is a flat character class on purpose (a nested group made it exponential on a long symbol run).

**WebP:** riven screenshots may be PNG, JPEG or WebP. `src/imaging/webp.ts` decodes WebP with libwebp compiled to WebAssembly (`@saschazar/wasm-webp`, no native module) and `scanCard` converts a WebP to a PNG first (`webpToPng`), so the rest of the image code stays PNG/JPEG only. The screenshot-roles reader is unchanged (a WebP there still goes straight to the vision models).

A person asking for a grade never triggers a crawl: `loadListings` uses stored listings younger than 6 h, else makes one read for that weapon (shared by simultaneous askers), falls back to older stored ones if warframe.market can't be read, and only then fails with a `UserError`. **Grading** (`grade.ts`, pure): the high bracket is the listings at or above `RIVEN_HIGH_PRICE`, or the weapon's top quarter (at least 8) when fewer reach it, and a weapon with under 16 listings gets no grade; the letter comes from where each bonus stat ranks among the bracket's most common bonus stats (top 3 = 2 points, top 6 = 1), S only when the exact combination also exists among the expensive ones; the embed also shows each stat's share, the value percentile among listed rolls (when a value was typed), the curse's share, and the asking prices of listings with the same bonuses (same curse when 3+ exist). **Prices come from a second, filtered request, not from the stored listings**, because one request only returns a weapon's 100 priciest, so anything computed from them leans high: `fetchComparable` asks `positive_stats=<slugs>&negative_stats=<slug>&sort_by=price_asc&buyout_policy=direct` when someone grades (user-facing, cached 30 min, never stored), keeps only listings that really carry exactly the graded bonuses, and `complete` means fewer than a page (100) came back, i.e. that is everything for sale (count, range and median are right); otherwise only the cheapest and 10th cheapest are shown. If the market refuses the filtered search with 400/422 it is not tried again for 6 h, and any failure falls back to the stored priciest listings, which the embed labels as such (`source: 'top'`); the value percentile is likewise only among those priciest listings. The filter parameter names come from the old v1 API docs and were not verified against the live API: if grades always show the "priciest listings" wording, the filter is being refused. **Unreadable stat lines are interpreted, not refused** (the owner: "always try to interpret what it could be"): `scanCard` first reads the cleaned picture (and the original when that is poor), then, when a stat line is unreadable, `pointer.ts` (`erasePointer`) paints a mouse pointer (a compact, taller-than-wide, colourless near-white shape, searched only in the band of the failed line so the artwork's white is never touched) out of the picture and it is read again (this recovered `Critical Chance` under the pointer in the real Zarr card), and `interpretUnknown` (`card.ts`) works out what is still unreadable from the line's value and sign, the stats the card does not already have (a minus can't be a positive-only stat) and the best fit between what is left of the name in EVERY OCR reading and each stat name (a small bonus for common stats breaks ties). **The answer to a scan is a picture** (`picture.ts`, `reply.ts`; `rolls.ts`): the owner asked for the look of an overlay tool: the card on the left and, on the right, the weapon name and one block per stat, `+101.3% Heat:` then `Grade:  A+  (+9.159%)` in a colour from green to red, **a grade for every roll, not for the riven as a whole**. A stat's value is random within 90%-110% of an average that depends on the weapon, the stat and the number of bonuses/curses; the percentage is where the roll sits in that range (+10 is the best possible roll) and for a curse a milder value is the better one. The average comes from the wiki's fixed ranges (`ranges.ts`, generated from the Riven Mods page: a base value per stat and kind of weapon (rifle, shotgun, pistol, archgun, melee) times a disposition times the layout weight, `WEIGHTS`: 2 bonuses 0.99, 2+curse 1.2375/0.495, 3 bonuses 0.75, 3+curse 0.9375/0.75). `gradeByTable` (rolls.ts) tries each kind of weapon (the market's `rivenType` first when its list gives one, else rifle, pistol, shotgun, archgun, melee) with the weapon's own disposition (old rivens were rolled with it; the reference card is a pistol-type Arca Scisco at 1.1 and reproduces to 0.1%) and the wiki's current constant 1.2, and takes the first combination in which EVERY stat of the card falls inside its 90%-110% window (so a rifle's damage range is not mistaken for a pistol's). **Screenshot roles** (`src/ssroles/`, `/setup ssroles`): members post their in-game Profile screenshot in a dedicated channel and Ordis gives them roles. **The readers run in this order: 1. OCR, 2. the self-hosted Gemma on Ollama, 3. Gemini; images are never stored:** everything runs in memory, the member's message stays while Ordis replies to it and is deleted together with the reply `ssTimings.resultTtlMs` (a minute) after the result is shown, and the DB keeps only a sha256 and the in-game name (`ss_claims`, so a card can't be shared between accounts) plus a 256-byte grayscale fingerprint of the clan emblem and the clan's `Name#043` line (`ss_reference`, learned from `/setup ssroles reference:` and optionally `reference2:`: each picture is recognized by what it shows, a profile card teaches the emblem (two cards are stored back to back and the best match counts) and a clan roster row is only checked). `ocr.ts` is tesseract.js (WebAssembly, so no native dependency in the amd64-to-arm64 image; the English data comes from the `@tesseract.js-data/eng` npm package, `cacheMethod: 'none'`, one lazily created worker released after 5 idle minutes). `parse.ts` turns OCR lines into a `CardReading` (pure, tested on real OCR output; the rank is checked against the mastery-point curve, MR n needs 2500n² points and Legendary n needs 2,250,000 + 147,500n, and a title that disagrees counts as unreadable). `emblem.ts` decodes PNG/JPEG with pngjs/jpeg-js, finds the emblem as the picture above the clan name line (band scaled by the line height, found by difference from the panel colour) and compares fingerprints by Pearson correlation (`MATCH_THRESHOLD`). When OCR can't produce a complete card, the image is not PNG/JPEG, or the emblem can't be located, `vision.ts` (`readProfileCardVia`) asks the self-hosted `LOCAL_AI_*` model (Gemma on Ollama; thinking off, 120 s+ timeout; no limit, but 25-50 s per image on a CPU, and in early tests it flagged untouched cards as edited and missed roster rows) and, when that is missing, switched off, paused after failing (`markLocalDown`) or unable to read the image, the free-tier cloud model (the `FREE_AI_*` endpoint, daily allowance `allow()`); that path compares the clan text but not the emblem, and the mod log names the reader (`readerLabel`). `readLocal`/`readCloud`/`readWithOcr` (service.ts) each run one method, which the panel's **Screenshots** page (`src/web/admin/sstest-page.ts` + `sstest-client.ts`, `/admin/sstest`) uses: upload a picture (raw body, CSRF in the `X-CSRF-Token` header, streamed back as NDJSON with pings because a CPU model can take minutes) and run OCR, Gemma and Gemini separately or in order, seeing the reading, timing, recognised text and what `checkClan` would decide; the test ignores the Local switch and pause, does not count against the cloud allowance, stores nothing and changes no roles. `roles.ts` is pure: `checkClan` (name must equal `CLAN_NAME`; with a reference, `Name#tag` must match and the emblem must not differ), `masteryRank` (Legendary N = MR 30+N) and `planRoles`, which only uses roles that already exist and match by normalized name (`MR 33`, `Legendary 3`, `Clan`, the clan name, accolade titles); managed roles, roles above Ordis and roles with moderator permissions are skipped, and leadership, moderation and admin roles are **never** handed out by name (`isStaffRoleName`: Leadership, Founding Warlord, Rat Emperor/King/Lord/Count/Baron, Enhanced Permissions, anything with admin, moderator, staff or owner, the bot roles), so an edited picture naming one gets nothing, and mastery roles are one-at-a-time (older ones are removed). Roles are only given when the clan check passes. **Clan rank:** a second kind of screenshot, the row of the in-game clan member list (name and rank title such as `Rat Squire`), is recognized when OCR finds no profile card (`parseRankRow`, tolerant of one wrong letter); A message may carry both pictures (up to two are read; `handleSsMessage` reads all of them first, then handles profile cards before rows so the row's name can be one the card just verified, and answers once with one embed per picture; `test/ssroles-both.test.ts` drives it with a stub message). `handleRankRow` gives only the ranks in `SELF_SERVE_RANKS` (Rat Squire, Rat Knight; Baron and above are leadership-only, withheld because Baron needs 1000 hours a picture can't show), requires the row's name to be one the member verified with a profile card (`ownsName` against their `ign` claims, so a borrowed row is refused), and for Rat Knight an `MR 16+` role (`RANK_MIN_MASTERY`). The sticky shows two example pictures (`stickyImages`: up to two space-separated links, served as `/ss-example.png` and `/ss-example-rank.png`). The handler runs after the honeypot and before chat in `bot.ts`, does not need Message Content (with the intent off the gateway delivers messages with no attachments, which would make every screenshot look like chatter to remove, so a message without any is first re-read over REST with `message.fetch()`, and left alone if that fails), goes by the file header and not Discord's content type (`normalizeImage`, `src/imaging/sniff.ts`: a pasted PNG arrives labelled image/webp, which made OCR skip it and sent it to Gemma, which misread the clan as "The Rats Den#69"; a real WebP is converted to PNG), and logs to the mod log.

**Sticky messages** (`src/sticky/service.ts`, `src/discord/commands/sticky.ts`, `/sticky set|edit|remove|list`, needs Manage Messages): not Discord pins. `set` and `edit` open a modal (heading, multi-line message, optional picture link; `edit` is prefilled), routed by the `sticky:save:<channelId>:<clean|keep>` custom ID in `bot.ts`; both run `checkStickyChannel` before the form and `saveSticky` after it. `StickyKeeper.onMessage` runs for every guild message (a cheap `stickies` lookup): after a 3 s debounce, capped by a 15 s max-wait so constant chat can't starve it, it posts a fresh copy of the sticky embed and then deletes the old one, so Ordis is the last speaker. Its own post is ignored (stored message id, plus a `busy` flag while reposting), `lastMessageId` skips a repost when the sticky is already last, and `saveSticky` forces one. Mentions are suppressed. **Clean mode** (`deleteOthers`) deletes everything other members post on arrival (staff with Manage Messages exempt), so the sticky is the only message and never needs reposting; it is refused in the chat, screenshot and verify channels, where Ordis has to read the message first. The screenshot channel's instructions are its sticky (`setupSsRoles` calls `saveSticky`), and its handler deletes non-screenshots itself. `StickyKeeper.onMessage` ignores that channel (`ssRolesChannelId`), so the instructions are never deleted and reposted: screenshots and replies remove themselves, so the sticky stays put.

**Leveling** (`src/leveling/`, `src/discord/commands/levels.ts`): Arcane/MEE6-style XP, on by default (`/setup levels [channel]` to choose the announcement channel, `/setup off feature:Leveling` to disable; stored as `levelingOff`/`levelChannelId`). `xp.ts` is pure: a level costs `5n²+50n+100` XP, a message earns 15-25 XP with a 60 s cooldown, voice earns 10 XP/min, and `planLevelRoles` picks the highest existing "Level N+" role at or below the level (matched by name via `levelTier`) and removes the other tiers, skipping managed roles and roles above Ordis. Only total XP is stored (`member_xp`); the level is derived. `service.ts` has `handleLevelMessage` (a separate call in the `MessageCreate` handler, ignoring bots, the honeypot/screenshot/verify channels, clean-sticky channels and `/xp ignore` channels), the level-up announcement and `LevelVoiceTicker` (members in a voice channel with another human, not deafened or muted, not AFK). Voice XP never touches the message cooldown. Commands: `/rank [member]`, `/leaderboard [page]`, and staff `/xp give|setlevel|reset|ignore|sync`. **Level 10 reward:** AttachFiles + EmbedLinks live only on the server roles Level 10+…60+ and on leadership/staff roles (Leadership, Rat Lord/King/Count), not on `Clan` or `@everyone`; because members hold one tier role, every new tier must carry both. The media channel and the ss-roles channel (attachments) override this for @everyone. The announcement adds a note when level 10 is crossed (`MEDIA_LEVEL`).

**Audit log** (`src/logging/`, `/setup auditlog`): `attachAuditLogging` (called in `index.ts`) posts deleted messages (author, channel, text, attachment names), edits (before/after), bulk deletes, voice joins/leaves/moves, and every Discord audit log entry (`GuildAuditLogEntryCreate`, so role, channel, member, invite, emoji and server changes say who did them; the `$add`/`$remove` of a role update list the roles) to the audit channel, falling back to the moderation log channel. It needs the unprivileged `GuildModeration` intent plus the bot's View Audit Log permission, and Message Content for message text (without it, texts show as not cached). Partials include `Message`, so deletes of uncached old messages still arrive (author and text unknown). Member joins and leaves need the Server Members intent: `ENABLE_MEMBER_LOGGING=true` (or `ENABLE_WELCOME`) plus the Developer Portal switch. Ordis's own messages, the screenshot channel, clean-sticky channels, the log channels and Ordis's own role/nickname changes (reported elsewhere) are skipped. `format.ts` holds the pure embed builders (`test/audit.test.ts`).

**Status reports** (`src/lifecycle.ts`, `/setup status`): `reportStart` (on `clientReady`) and `reportStop` (first thing in `shutdown`, bounded by a 4 s timeout so it can't hold up Docker's stop; a restart from the panel or the MCP goes through the same `shutdown` because `index.ts` registers it with `onRestart` in `src/selfupdate.ts`, and `scheduleRestart` gives it 8 s before it exits anyway) post to the staff `statusChannelId`. `bot_meta` keeps `lifecycle_state` (`running`/`stopped`), so a start after `running` is reported as an unclean stop (crash/kill) and after `stopped` as a normal restart with the downtime.

**Shared service layer:** `src/services/clan.ts` holds every operation that posts to Discord (events, announcements, LFG rendering, channel resolution). `assertChannelFree(ctx, patch)` is the one rule for channels that read every message (chat, honeypot, verification, screenshot roles, riven scanning): a channel gets one job, and every place that assigns one (the `/setup` commands, the panel's settings form, MCP `update_bot_settings`) calls it before saving anything. `createClanEvent` refuses a start in the past or more than two years away. Slash commands and MCP tools both call it, so behaviour stays the same. Throw `UserError` for expected failures: Discord shows it ephemerally, and MCP returns it as an `isError` tool result. Any other error is logged and shown generically. `getSendableChannel` refuses channels outside the clan guild.

**Persistence:** `src/db.ts` uses the built-in `node:sqlite` (`DatabaseSync`, synchronous), so there are no native npm deps. That's also why the Dockerfile can build on `$BUILDPLATFORM` and copy `node_modules` into the arm64 image. The schema is versioned through `PRAGMA user_version` and the append-only `MIGRATIONS` array: never edit a shipped migration, add a new entry. Times are stored as epoch ms. Tests use `new Store(':memory:')`.

**Warframe data** (`src/warframe/`):
- Worldstate is off by default (`WORLDSTATE_ENABLED=false`; switch it on in the Config page). It comes from the community warframestat.us API, `api.warframestat.us/<platform>` (`pc`, `ps4`, `xb1`, `swi`, chosen from `WARFRAME_PLATFORM`), which serves the already-parsed world state as JSON (dates are ISO strings, so go through `toMs`/`discordTime`/`relative` in `src/time.ts`, which tolerate strings and missing values). **Never call Digital Extremes' own `api.warframe.com`** (calling it yourself breaches their EULA, and a blocked IP can't log in to the game either; the clan's co-owner asked for it to be removed fully): `worldstate.ts` has no code for the raw feed, `WORLDSTATE_URL` only accepts a warframestat.us-compatible JSON endpoint, and `parse()` rejects anything else. The types still come from `warframe-worldstate-parser` (`import type` only, nothing from it is loaded at runtime). It is called at most once per `WORLDSTATE_POLL_SECONDS` (default 600): the last call (time, result, url) is kept in `bot_meta` and the answer in `<DATA_DIR>/worldstate.cache`, so restarts and deploys cause no extra calls (a record or validators for another url are ignored); after a failure it waits `retryAt`. **Smart polling** (option, `WORLDSTATE_SMART_POLL`, off by default; `WORLDSTATE_MAX_POLL_MINUTES`, default 30): instead of a fixed timer the next call is due at the soonest rollover (`nextRefreshDelay`: alerts, sortie, archon hunt, events, Baro arrival or departure, daily deals, Zariman and Duviri cycles, Steel Path rotation, bounties) plus 20 s, never sooner than `WORLDSTATE_POLL_SECONDS` and never later than the cap. Fissures are deliberately not rollovers (dozens of them, one is always about to end, so it would poll at the minimum all day); they refresh with the cap and ended ones are filtered out meanwhile. `cached.due` holds the due time, also computed for the answer reloaded from disk after a restart. `test/worldstate-smart.test.ts` uses a mocked Date. The status page shows a "World state" pill with the last call.
- warframe.market must use **API v2** (v1 returns 403 "Deprecated"). Its Cloudflare blocks Node's default User-Agent, so every outbound call goes through `apiFetch` in `src/warframe/fetch.ts`.
- Drop tables come from warframestat.us (`/drops/search/`), which still works.

Discord-facing formatting lives in `src/discord/embeds.ts`. MCP returns plain JSON built by `src/mcp/worldstate-summary.ts`, with no Discord markup and ISO times plus an "in 2h 5m" string.

## Deployment

`.github/workflows/docker-publish.yml` runs typecheck and tests, then buildx builds `linux/amd64,linux/arm64`. It pushes to Docker Hub (except on PRs) using the secrets `DOCKER_USERNAME`/`DOCKER_PASSWORD`. The image is `vars.DOCKERHUB_IMAGE`, or `<username>/rats-den-warframe-bot` when that variable is unset. Tags: `latest` on main, semver on `v*.*.*` tags, and `sha-<short>`. Runtime data goes in `/app/data` (a volume). `.mcp.json` points Claude Code at the running bot via `RATS_DEN_MCP_URL`/`RATS_DEN_MCP_TOKEN`.

`docker-compose.yml` is the production stack: `bot` plus `caddy` (`caddy reverse-proxy` CLI, automatic HTTPS for `BOT_DOMAIN`, so there's no Caddyfile) plus `watchtower`. Watchtower uses the maintained `nickfedor/watchtower` fork, since `containrrr/watchtower` is archived. It updates only containers labelled `com.centurylinklabs.watchtower.enable=true`, which means only `bot`. The bot's settings are passed one by one through `environment:` interpolation instead of `env_file`, so the same file works with a local `.env` and as a Portainer stack. A new bot env var therefore has to be added in `src/config.ts`, `.env.example` and the `bot.environment` block of the compose file. The live deployment runs as a Portainer stack with values inline (no Caddy: a Cloudflare Tunnel points at the bot's port), so new settings also need adding there.
