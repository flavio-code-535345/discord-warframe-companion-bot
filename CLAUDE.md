# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

"Cephalon Ordis", the Discord bot for the Warframe clan "The Rats Den 69" (TypeScript, ESM, Node 24, discord.js v14). It also serves an MCP server over HTTP and is published as a Docker image (`flavio11113/rats-den-warframe-bot`) to Docker Hub by GitHub Actions.

**Identity:** `src/discord/identity.ts` syncs the bot's Discord username (`BOT_NAME`) and avatar (`assets/clan-logo.png`, which the Dockerfile copies into the image) on every `ClientReady`. It only calls the API when something differs, because Discord rate-limits both; the avatar hash is kept in the `bot_meta` table. Embeds use `brandIcon(ctx)` (the bot's avatar URL) for icons, and `COLORS.brand` is the crystal blue sampled from the logo.

## Commands

```bash
npm run dev          # tsx watch, loads .env (copy .env.example first)
npm run typecheck    # tsc --noEmit over src + test
npm test             # node:test via tsx, all test/**/*.test.ts
npx tsx --test test/db.test.ts                         # one file
npx tsx --test --test-name-pattern="markSeen" test/db.test.ts   # one test
npm run build        # tsc -p tsconfig.build.json → dist/
npm start            # node dist/index.js
```

TypeScript is v7 (native `tsc`). Relative imports must use `.js` extensions (NodeNext resolution).

## Architecture

`src/index.ts` builds one `AppContext` (`config`, `store`, discord `client`, see `src/context.ts`) and hands it to three consumers that run in the same process:

1. **Discord interactions** (`src/discord/bot.ts`): routes slash commands (`src/discord/commands/*`, each exporting a `Command`), autocomplete, and buttons (`src/discord/buttons.ts`). Commands are registered **guild-scoped** to `DISCORD_GUILD_ID` on every `ClientReady`; the bot deliberately serves only that one guild. Button custom IDs are `rsvp:<eventId>:<going|maybe|declined>` and `lfg:<postId>:<join|leave|close>`, so they keep working after restarts.
2. **Notifier** (`src/discord/notifier.ts`): wakes every minute (event reminders) and uses the worldstate, which is fetched at most every `WORLDSTATE_POLL_SECONDS`. `collectAlerts()` is a pure function that returns every currently alert-worthy item with a stable `key`; `Store.markSeen(key)` de-duplicates across restarts. On an empty `seen_worldstate` table it records the current items without posting (no flood on first deploy). It also sends event reminders 15 minutes before start.
3. **HTTP server** (`src/http.ts`): the public status page `/` plus `/status.json` and `/logo.png` (`src/web/status.ts`). The page is a dense tile dashboard (CSS `columns` masonry). `worldOf()` builds each tile's data inside its own try/catch, so one malformed worldstate section can't blank the page. The page and its JSON are server-rendered with no build step; the page's inline style and script are allowed by a per-request CSP nonce, and every dynamic string goes through `escapeHtml`. `buildStatus` reads only cached Discord data and exposes aggregates, never member names or IDs. There's also `/health` (no auth, used by the Docker HEALTHCHECK) and, only when `MCP_AUTH_TOKEN` is set, `POST /mcp`. Express 5 reports listen errors through the `app.listen` callback, and the bot exits on them. MCP is **stateless Streamable HTTP**: a new `McpServer` (`src/mcp/server.ts`) and transport are built per request, so `createMcpServer` must not do I/O. Bearer auth runs before body parsing; `MCP_ALLOWED_HOSTS` adds DNS-rebinding Host checks.

**Free chat answers** (`src/answers/`): the default when there's no `ANTHROPIC_API_KEY`, and what the deployed bot uses (the owner won't pay for an AI API). `detectIntent()` in `intent.ts` is pure regex/keyword rules mapping a message to a lookup (price, drops, relic, world view, fissures, bounties, clan events, build, item, wiki fallback). Rule order matters: price before relic, and drops before world views. `test/intent.test.ts` pins real phrasings, so add a case when changing a rule. `smart.ts` turns an intent into an Ordis line plus an existing embed, and falls back to `searchWiki`, which prefers a page whose title appears in the question. `found: false` lets the chat channel stay silent. In the `/setup chat` channel `isChannelQuestion()` decides what Ordis picks up: anything ending in `?` or an intent that names a concrete lookup (not help/item/wiki), minus greetings like "good night".

**Local model (Ollama)** (`src/answers/compose.ts`): `LOCAL_AI_URL` + `LOCAL_AI_MODEL` (+ optional `LOCAL_AI_KEY`, `LOCAL_AI_TIMEOUT_SECONDS` default 60) point `composeAnswer` at a self-hosted OpenAI-compatible server (Ollama `/v1`, reached over Tailscale or a tunnel). It is tried before the free cloud endpoint, has no daily limit, and a failure or timeout skips it for `LOCAL_COOLDOWN_MS` (3 min) so a sleeping host doesn't slow every question; a clean answer, including NOT_COVERED, is final. Only the free chat answers use it (not the screenshot vision fallback, which still needs `FREE_AI_KEY`). New vars follow the usual rule: config.ts, .env.example, compose, Portainer YAML.

**`/ai` command** (`src/discord/commands/ai.ts`, Manage Server): `/ai status`, `/ai model name:` (autocomplete from Ollama's installed models; `-` returns to `LOCAL_AI_MODEL`) and `/ai install tag:` (background download, one at a time, posts in the channel when done). The choice is kept in `bot_meta` (`local_ai_model`), loaded at startup, and wins over `LOCAL_AI_MODEL` everywhere through `localModelOf` (`src/ai/ollama.ts`, which also holds the Ollama API helpers shared with the MCP tools). **Ollama stack and MCP tools:** `docker-compose.ollama.yml` is a separate stack for the machine with the RAM (tailscale sidecar, ollama, a one-shot `pull-model`); the bot reaches it over the tailnet. With `LOCAL_AI_URL` set, `src/mcp/ollama.ts` registers `ollama_status` (reachable, installed and loaded models, background download progress), `ollama_pull` (background download, one at a time) and `ollama_test` (timed answer), using Ollama's native API at the URL without `/v1`.

**AI question log** (`src/answers/log.ts`, `/ailog`, table `ai_log`): every free answer given in the chat channel, in DMs or by `/ask` is recorded with asker, channel, question, intent, source (`local` Ollama, `cloud`, `excerpt`, `lookup`), model, milliseconds and the start of the answer, and pruned after 30 days. `smartAnswer` fills `source/model/intent/ms` (via `composeDetailed`, which says which endpoint wrote the text); `logAnswer` never throws. `/ailog [count] [member]` (Manage Messages) shows the newest entries plus the last 24 h per source. The Claude (`ctx.ai`) path is not logged.

**Insight MCP tools** (`src/mcp/insights.ts`): `get_ai_log` (questions, answers, source and model, with counts by source/intent, unanswered and repeated questions), `get_bot_health` (uptime, Discord, lifecycle, Warframe API pacing, configured models and whether the local one is being skipped, wiki index, answers in 24 h, which features are on), `list_member_levels` and `set_member_level` (lifts members to a level with `only_raise`, updates their Level roles; max 50 per call). `update_bot_settings` also takes `audit_log_channel_id`, `status_channel_id` and `level_channel_id`.

**Claude chat (optional)** (`src/ai/`): `OrdisBrain.ask()` runs Claude through the SDK's beta tool runner (`client.beta.messages.toolRunner` with `betaZodTool` tools that reuse the same Warframe functions as the slash commands and MCP), plus the `web_search_20260209` server tool restricted to Warframe domains. The runner doesn't resume `pause_turn` by itself, so `ask()` pushes the paused turn back. The system prompt and tool order are a stable, cached prefix; per-request context (time, asker, channel) goes in the user turn. `fallbacks: "default"` + beta `server-side-fallback-2026-07-01` is sent only for model families that support it (not Haiku). Conversation history comes from the Discord reply chain (`src/discord/chat.ts`); each answer chunk replies to the previous one so that replying to any chunk continues the thread. `AskLimiter` is in-memory. Without `ANTHROPIC_API_KEY`, `ctx.ai` is null and chat is off. `test/ai.test.ts` drives the real SDK against a fake `fetch`, so it checks the request shape without spending money.

**Trackers** (`src/trackers.ts`): `collectTrackables(ws)` turns the worldstate into keyed items (invasions, alerts, Darvo, events, Steel Path, Varzia, Baro, fissures, cycle phases) and `matchTracker(spec, item)` is pure. The notifier de-duplicates per tracker with `seen_worldstate` keys `track:<id>:<item key>` and sends one DM per member per poll.

**Wiki index** (`src/wiki/`): `crawler.ts` lists every main-namespace article with its latest revision (`generator=allpages&prop=info`, 500 per request), downloads only the changed ones as wikitext (40 per request, `prop=revisions&rvslots=main`), and removes deleted ones; it refuses to shrink the index below half its size (a truncated listing must not wipe it). `clean.ts` turns wikitext into plain text (nested template removal with a small allowlist of display-only templates, tables flattened to rows, links and markup stripped) and splits it into ≤1000-character chunks by heading. `index.ts` stores them in an FTS5 table (porter stemming) in its own `wiki.db`, deliberately outside `bot.db` so it never bloats backups or migrations. `search()` puts the page whose title appears in the question first (shell pages like `Kuva Lich` fall through to `Kuva Lich/Main`), then bm25 matches (all words, then most words); patch-note pages are excluded unless the question mentions updates. `searchWiki`/`readWikiPage` in `warframe/wiki.ts` consult the index first once it has 500+ pages, and fall back to the live API, so every consumer (chat, `/wiki`, MCP, Claude) benefits. The wiki's full-page extracts are limited to one page per request, which is why this reads wikitext instead.

**Lookups** (`src/warframe/items.ts`, `wiki.ts`): warframestat.us `/items/search` for stats (a relic's four refinements are merged into one result, and rarity is derived from the intact chance because the export's labels are unreliable). Drop chances in both warframestat.us APIs are already percentages. The wiki uses MediaWiki `list=search` plus TextExtracts.

**Moderation** (`src/moderation/`, commands in `src/discord/commands/moderation.ts`): `purge.ts` keeps message selection pure (`selectForPurge`) and splits bulk-deletable messages (under 14 days) from old ones, which are deleted one at a time up to `OLD_DELETE_CAP`. Large or `all` purges wait for a confirmation button (`purge:<token>:<confirm|cancel>`, pending requests are kept in memory). `service.ts` has `assertCanAct` (role hierarchy against the moderator and Ordis), `modLog` (posts to the `/setup modlog` channel) and `lockChannel`/`unlockChannel`. Lock stores each overwrite's previous SendMessages state in `channel_locks`, so unlock restores it exactly. Lock skips roles with Administrator or Manage Messages. `honeypot.ts` is the trap channel (`/setup honeypot`): `handleHoneypotMessage` runs before the chat handler on every message and returns true for anything posted in the trap channel, so Ordis never also answers there. Staff, the owner, Ordis and anyone at or above Ordis's role are exempt (`isHoneypotExempt`). The default action is `softban` (ban with a 1h message delete, then unban); it needs no Message Content intent.

**Backups** (`src/backup/`): `snapshot.ts` serializes the guild (bitfields as decimal strings; icon and emojis as base64 so they outlive the CDN; messages only with the Message Content intent) into `backups.data`. A small `summary` JSON sits next to it so listings stay cheap. `service.ts` holds `takeBackup` (single-flight) and `BackupScheduler` (daily, keeps 14 automatic backups). `restore.ts`: `planRestore` is pure and powers the confirmation preview. `restoreBackup` maps backup IDs to live or recreated IDs (roles first, then categories, then channels, then one bulk `setPositions`). It never deletes, it downgrades Community-only channel types, and it re-points Ordis's settings. The `/backup load` confirmation always takes a safety backup first. `test/backup.test.ts` drives the restore against an in-memory fake Guild.

**Verification** (`src/verification/`, `src/discord/verification.ts`): `captcha.ts` draws captchas in pure JS (a 5×7 bitmap font plus shear, noise and a sine warp, encoded as PNG with `zlib`). No canvas or native module: the Docker build copies amd64 `node_modules` into the arm64 image, so native packages would break. `attempts.ts` is the in-memory challenge state: wrong answers count across refreshes, then a cooldown. Custom IDs are `verify:start|refresh|answer` and the modal is `verify:modal`. Only the role is handed out; channel overwrites do the gating. `assertSafeVerifyRole` refuses roles with moderator or admin permissions. Guild settings live in the `SETTINGS_COLUMNS` table in `db.ts`, so a new setting means a migration plus one line there.

**Admin panel** (`src/web/admin/`): an Express router mounted at `/admin`, server-rendered with no client script. Its CSP allows styles by nonce, images from self and cdn.discordapp.com, and form posts to self. `auth.ts` has the Discord OAuth code flow (`identify` scope, with a state cookie), HMAC-signed cookies (the key is in `bot_meta`) and `isPanelAdmin` (`PANEL_OWNER_IDS` plus the `panel_admins` table). `routes.ts` has the `guard`, which re-checks the whitelist on every request and the CSRF token on every POST. `action()` handles POST-redirect-GET with `?ok=` / `?err=` flash messages, and `audit()` writes to the mod log. The panel is off (and serves a 503 explanation) until `DISCORD_CLIENT_SECRET` and `PUBLIC_URL` are set. `test/admin.test.ts` drives it over HTTP with a stub client.

**Server admin over MCP** (`src/mcp/admin.ts`): `get_server_structure` plus create/edit/reorder/permission/archive tools for restructuring the clan Discord. Channels are never deleted: `archive_channel` moves one into a hidden "🗄️ Archive" category and returns its old state. The only destructive tool is `clear_messages` (needs `confirm: true`; pair it with `read_messages` first). Positions are indexes within the parent category, because discord.js re-sorts siblings. Overwrites at creation need an explicit `OverwriteType`, since a member ID that isn't cached can't be inferred.

**Live code patches** (`src/overlay.ts`, `src/overlay-register.ts`, `src/mcp/code.ts`): with `ALLOW_CODE_EDIT=true` the MCP gets `list_code_files`, `read_code_file`, `write_code_file` and `revert_code_file`, which patch the compiled JavaScript in `dist` without a new image. This is remote code execution for whoever holds `MCP_AUTH_TOKEN`, so it is off by default. A patch is saved as an override in `<DATA_DIR>/overlay/` (with the sha256 of the image file it replaces, after a `node --check` syntax check) and takes effect on the next restart: the Docker CMD preloads `dist/overlay-register.js`, whose `module.registerHooks` load hook swaps in the override's source but keeps the file's original URL, so its relative and package imports still resolve from the image. Safety nets: an override whose image file changed in a newer image is dropped at startup; and a start with active overrides arms `boot.lock`, which `index.ts` clears after `SAFE_BOOT_MS` (15 s) of uptime, so if the bot died before that the whole overlay is renamed to `overlay.disabled-<ts>` on the next start. Patches are a stopgap: put the same change in the repo. `test/overlay.test.ts` runs a real node process with the preload.

**Squad voice and activities** (`src/lfg/`): with `/setup lfgvoice`, `/lfg` creates a voice channel per squad (`voice.ts`). `lifecycle.ts` holds the pure rules (`sweepAction`: expiry, host-absent grace period, delete a closed squad's channel once empty), so they're testable without Discord. A once-a-minute `LfgVoiceSweeper` applies them, which survives restarts and needs no per-channel timers; it reads who is in a channel from the cache, so the (unprivileged) GuildVoiceStates intent is required. `hostAbsentSince` starts at creation, so a host who never joins voice still ends the squad. The `activities` table (case-insensitive name, image URL, ping role, fixed channel) feeds `renderLfg` (thumbnail) and `/lfg` (ping and channel); activities without a row still work. `autovc.ts` is join-to-create (`/setup autovc`): `handleVoiceStateUpdate` (a `VoiceStateUpdate` listener) makes a room per member in the lobby's category and deletes it when empty; rooms are tracked in `temp_voice` and `sweepTempVoice` (same minute timer) removes empty or vanished ones, sparing rooms younger than 30s so the owner can be moved in. `/vc` is owner-only and checks `temp_voice`. Image URLs must pass `validImageUrl` (plain https), which is why the admin panel's CSP allows `img-src https:`.

**Screenshot roles** (`src/ssroles/`, `/setup ssroles`): members post their in-game Profile screenshot in a dedicated channel and Ordis gives them roles. **OCR is the main reader, Gemini the fallback, and images are never stored:** everything runs in memory, the member's message is deleted right after the read, and the DB keeps only a sha256 and the in-game name (`ss_claims`, so a card can't be shared between accounts) plus a 256-byte grayscale fingerprint of the clan emblem and the clan's `Name#043` line (`ss_reference`, learned from `/setup ssroles reference:` and optionally `reference2:`: each picture is recognized by what it shows, a profile card teaches the emblem (two cards are stored back to back and the best match counts) and a clan roster row is only checked). `ocr.ts` is tesseract.js (WebAssembly, so no native dependency in the amd64-to-arm64 image; the English data comes from the `@tesseract.js-data/eng` npm package, `cacheMethod: 'none'`, one lazily created worker released after 5 idle minutes). `parse.ts` turns OCR lines into a `CardReading` (pure, tested on real OCR output; the rank is checked against the mastery-point curve, MR n needs 2500n² points and Legendary n needs 2,250,000 + 147,500n, and a title that disagrees counts as unreadable). `emblem.ts` decodes PNG/JPEG with pngjs/jpeg-js, finds the emblem as the picture above the clan name line (band scaled by the line height, found by difference from the panel colour) and compares fingerprints by Pearson correlation (`MATCH_THRESHOLD`). When OCR can't produce a complete card, the image is not PNG/JPEG, or the emblem can't be located, `vision.ts` asks the free-tier vision model (the `FREE_AI_*` endpoint) instead, and when that is missing, down or over its daily allowance the self-hosted `LOCAL_AI_*` model (Gemma 4 on Ollama) is the backup (thinking off, 120 s+ timeout; in tests it read rank and clan right but flagged untouched cards as edited and missed roster rows, and took 25-50 s per image on a CPU, so it is deliberately behind the cloud reader); that path compares the clan text but not the emblem, and the mod log says so. `roles.ts` is pure: `checkClan` (name must equal `CLAN_NAME`; with a reference, `Name#tag` must match and the emblem must not differ), `masteryRank` (Legendary N = MR 30+N) and `planRoles`, which only uses roles that already exist and match by normalized name (`MR 33`, `Legendary 3`, `Clan`, the clan name, accolade titles); managed roles, roles above Ordis and roles with moderator permissions are skipped, and leadership, moderation and admin roles are **never** handed out by name (`isStaffRoleName`: Leadership, Founding Warlord, Rat Emperor/King/Lord/Count/Baron, Enhanced Permissions, anything with admin, moderator, staff or owner, the bot roles), so an edited picture naming one gets nothing, and mastery roles are one-at-a-time (older ones are removed). Roles are only given when the clan check passes. **Clan rank:** a second kind of screenshot, the row of the in-game clan member list (name and rank title such as `Rat Squire`), is recognized when OCR finds no profile card (`parseRankRow`, tolerant of one wrong letter); A message may carry both pictures (up to two are read; `handleSsMessage` reads all of them first, then handles profile cards before rows so the row's name can be one the card just verified, and answers once with one embed per picture; `test/ssroles-both.test.ts` drives it with a stub message). `handleRankRow` gives only the ranks in `SELF_SERVE_RANKS` (Rat Squire, Rat Knight; Baron and above are leadership-only, withheld because Baron needs 1000 hours a picture can't show), requires the row's name to be one the member verified with a profile card (`ownsName` against their `ign` claims, so a borrowed row is refused), and for Rat Knight an `MR 16+` role (`RANK_MIN_MASTERY`). The sticky shows two example pictures (`stickyImages`: up to two space-separated links, served as `/ss-example.png` and `/ss-example-rank.png`). The handler runs after the honeypot and before chat in `bot.ts`, needs Message Content to see attachments, and logs to the mod log.

**Sticky messages** (`src/sticky/service.ts`, `src/discord/commands/sticky.ts`, `/sticky set|edit|remove|list`, needs Manage Messages): not Discord pins. `set` and `edit` open a modal (heading, multi-line message, optional picture link; `edit` is prefilled), routed by the `sticky:save:<channelId>:<clean|keep>` custom ID in `bot.ts`; both run `checkStickyChannel` before the form and `saveSticky` after it. `StickyKeeper.onMessage` runs for every guild message (a cheap `stickies` lookup): after a 3 s debounce, capped by a 15 s max-wait so constant chat can't starve it, it posts a fresh copy of the sticky embed and then deletes the old one, so Ordis is the last speaker. Its own post is ignored (stored message id, plus a `busy` flag while reposting), `lastMessageId` skips a repost when the sticky is already last, and `saveSticky` forces one. Mentions are suppressed. **Clean mode** (`deleteOthers`) deletes everything other members post on arrival (staff with Manage Messages exempt), so the sticky is the only message and never needs reposting; it is refused in the chat, screenshot and verify channels, where Ordis has to read the message first. The screenshot channel's instructions are its sticky (`setupSsRoles` calls `saveSticky`), and its handler deletes non-screenshots itself.

**Leveling** (`src/leveling/`, `src/discord/commands/levels.ts`): Arcane/MEE6-style XP, on by default (`/setup levels [channel]` to choose the announcement channel, `/setup off feature:Leveling` to disable; stored as `levelingOff`/`levelChannelId`). `xp.ts` is pure: a level costs `5n²+50n+100` XP, a message earns 15-25 XP with a 60 s cooldown, voice earns 10 XP/min, and `planLevelRoles` picks the highest existing "Level N+" role at or below the level (matched by name via `levelTier`) and removes the other tiers, skipping managed roles and roles above Ordis. Only total XP is stored (`member_xp`); the level is derived. `service.ts` has `handleLevelMessage` (a separate call in the `MessageCreate` handler, ignoring bots, the honeypot/screenshot/verify channels, clean-sticky channels and `/xp ignore` channels), the level-up announcement and `LevelVoiceTicker` (members in a voice channel with another human, not deafened or muted, not AFK). Voice XP never touches the message cooldown. Commands: `/rank [member]`, `/leaderboard [page]`, and staff `/xp give|setlevel|reset|ignore|sync`. **Level 10 reward:** AttachFiles + EmbedLinks live only on the server roles Level 10+…60+ and on leadership/staff roles (Leadership, Rat Lord/King/Count), not on `Clan` or `@everyone`; because members hold one tier role, every new tier must carry both. The media channel and the ss-roles channel (attachments) override this for @everyone. The announcement adds a note when level 10 is crossed (`MEDIA_LEVEL`).

**Audit log** (`src/logging/`, `/setup auditlog`): `attachAuditLogging` (called in `index.ts`) posts deleted messages (author, channel, text, attachment names), edits (before/after), bulk deletes, voice joins/leaves/moves, and every Discord audit log entry (`GuildAuditLogEntryCreate`, so role, channel, member, invite, emoji and server changes say who did them; the `$add`/`$remove` of a role update list the roles) to the audit channel, falling back to the moderation log channel. It needs the unprivileged `GuildModeration` intent plus the bot's View Audit Log permission, and Message Content for message text (without it, texts show as not cached). Partials include `Message`, so deletes of uncached old messages still arrive (author and text unknown). Member joins and leaves need the Server Members intent: `ENABLE_MEMBER_LOGGING=true` (or `ENABLE_WELCOME`) plus the Developer Portal switch. Ordis's own messages, the screenshot channel, clean-sticky channels, the log channels and Ordis's own role/nickname changes (reported elsewhere) are skipped. `format.ts` holds the pure embed builders (`test/audit.test.ts`).

**Status reports** (`src/lifecycle.ts`, `/setup status`): `reportStart` (on `clientReady`) and `reportStop` (first thing in `shutdown`, bounded by a 4 s timeout so it can't hold up Docker's stop) post to the staff `statusChannelId`. `bot_meta` keeps `lifecycle_state` (`running`/`stopped`), so a start after `running` is reported as an unclean stop (crash/kill) and after `stopped` as a normal restart with the downtime.

**Shared service layer:** `src/services/clan.ts` holds every operation that posts to Discord (events, announcements, LFG rendering, channel resolution). Slash commands and MCP tools both call it, so behaviour stays the same. Throw `UserError` for expected failures: Discord shows it ephemerally, and MCP returns it as an `isError` tool result. Any other error is logged and shown generically. `getSendableChannel` refuses channels outside the clan guild.

**Persistence:** `src/db.ts` uses the built-in `node:sqlite` (`DatabaseSync`, synchronous), so there are no native npm deps. That's also why the Dockerfile can build on `$BUILDPLATFORM` and copy `node_modules` into the arm64 image. The schema is versioned through `PRAGMA user_version` and the append-only `MIGRATIONS` array: never edit a shipped migration, add a new entry. Times are stored as epoch ms. Tests use `new Store(':memory:')`.

**Warframe data** (`src/warframe/`):
- Worldstate is off by default (`WORLDSTATE_ENABLED=false`) while DE's CDN blocks our IP with HTTP 403; `WORLDSTATE_URL` can point at a relay serving the raw feed. It comes from DE's official `api.warframe.com/cdn/worldState.php`, parsed locally with `warframe-worldstate-parser`. It is called at most once per `WORLDSTATE_POLL_SECONDS` (default 600): the last call (time, result) is kept in `bot_meta` and the raw answer in `<DATA_DIR>/worldstate.cache`, so restarts and deploys cause no extra calls; after a failure it waits at least 30 min. The status page shows a "Warframe API" pill with the last call. The warframestat.us `/pc` worldstate endpoint was returning 404, so don't switch back to it. The parser needs `import 'reflect-metadata'` to load first. Its models type most dates as `Date | undefined`, so go through `toMs`/`discordTime`/`relative` in `src/time.ts`, which tolerate missing values.
- warframe.market must use **API v2** (v1 returns 403 "Deprecated"). Its Cloudflare blocks Node's default User-Agent, so every outbound call goes through `apiFetch` in `src/warframe/fetch.ts`.
- Drop tables come from warframestat.us (`/drops/search/`), which still works.

Discord-facing formatting lives in `src/discord/embeds.ts`. MCP returns plain JSON built by `src/mcp/worldstate-summary.ts`, with no Discord markup and ISO times plus an "in 2h 5m" string.

## Deployment

`.github/workflows/docker-publish.yml` runs typecheck and tests, then buildx builds `linux/amd64,linux/arm64`. It pushes to Docker Hub (except on PRs) using the secrets `DOCKER_USERNAME`/`DOCKER_PASSWORD`. The image is `vars.DOCKERHUB_IMAGE`, or `<username>/rats-den-warframe-bot` when that variable is unset. Tags: `latest` on main, semver on `v*.*.*` tags, and `sha-<short>`. Runtime data goes in `/app/data` (a volume). `.mcp.json` points Claude Code at the running bot via `RATS_DEN_MCP_URL`/`RATS_DEN_MCP_TOKEN`.

`docker-compose.yml` is the production stack: `bot` plus `caddy` (`caddy reverse-proxy` CLI, automatic HTTPS for `BOT_DOMAIN`, so there's no Caddyfile) plus `watchtower`. Watchtower uses the maintained `nickfedor/watchtower` fork, since `containrrr/watchtower` is archived. It updates only containers labelled `com.centurylinklabs.watchtower.enable=true`, which means only `bot`. The bot's settings are passed one by one through `environment:` interpolation instead of `env_file`, so the same file works with a local `.env` and as a Portainer stack. A new bot env var therefore has to be added in `src/config.ts`, `.env.example` and the `bot.environment` block of the compose file. The live deployment runs as a Portainer stack with values inline (no Caddy: a Cloudflare Tunnel points at the bot's port), so new settings also need adding there.
