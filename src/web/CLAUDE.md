# Status page and admin panel

Notes for this folder. The rules that apply everywhere, the commands and the list of the other notes are in the root `CLAUDE.md`.

**HTTP server** (`src/http.ts`): the public status page `/` plus `/status.json` and `/logo.png` (`src/web/status.ts`). The page is a quiet header (logo, one online line) and a headline strip (next cycle change, Baro, Arbitration, sortie) above four collapsible sections (Open worlds and The Void open, Resets and Events and trading closed) of tiles in a CSS grid; open states survive the minute refresh; the Void fissures tile lists every open fissure with Steel Path/Storm/tier filter chips (client-side, kept in sessionStorage), alerts come from `groupAlerts` (worldstate.ts, shared with the alerts board, so an event's missions are one row), the Arbitration tile and headline come from the schedule (`buildStatus`'s third loader, `lastArbitrations`, no request: the hour running now with its tier, the next 6 hours and the S/A hours of the week, only the current one when the world state names another node), so they keep working while the world state is off; the tile, chip and headline icons are the clan's custom emojis on Discord's CDN (`renderStatusPage`'s `iconOf`, default `emojiUrl(name, 48)`; the status CSP allows `img-src https://cdn.discordapp.com`), and a name with only a Unicode stand-in just shows no icon; the inline script ticks the countdowns every second and re-fetches `/` every minute to swap in the new `<main>` without a reload (the CSP has `connect-src 'self'` for that). `worldOf()` builds each tile's data inside its own try/catch, so one malformed worldstate section can't blank the page. The page and its JSON are server-rendered with no build step; the page's inline style and script are allowed by a per-request CSP nonce, and every dynamic string goes through `escapeHtml`. `buildStatus` reads only cached Discord data and exposes aggregates, never member names or IDs. `/` and `/status.json` are open to everyone and read the database, so one reading of the status data is shared by every visitor for `STATUS_TTL_MS` (5 s; a failed reading is not kept). Every answer carries `securityHeaders` (nosniff, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and HSTS when `PUBLIC_URL` is https; the panel sets its own referrer policy on top), and `errorHandler` is the last middleware: a failure is logged and answered with one line (a JSON-RPC error on `/mcp`), a refused body keeps its 400/413, and no stack is ever sent whatever `NODE_ENV` says. There's also `/health` (no auth, used by the Docker HEALTHCHECK) and, only when `MCP_AUTH_TOKEN` is set, `POST /mcp`. Express 5 reports listen errors through the `app.listen` callback, and the bot exits on them. MCP is **stateless Streamable HTTP**: a new `McpServer` (`src/mcp/server.ts`) and transport are built per request, so `createMcpServer` must not do I/O. Bearer auth runs before body parsing; `MCP_ALLOWED_HOSTS` adds DNS-rebinding Host checks.

**Admin panel** (`src/web/admin/`): an Express router mounted at `/admin`, server-rendered with no client script. Its CSP allows styles by nonce, images from self and cdn.discordapp.com, and form posts to self. `auth.ts` has the Discord OAuth code flow (`identify` scope, with a state cookie), HMAC-signed cookies (the key is in `bot_meta`) and `isPanelAdmin` (`PANEL_OWNER_IDS` plus the `panel_admins` table). `routes.ts` has the `guard`, which re-checks the whitelist on every request and the CSRF token on every POST. `action()` handles POST-redirect-GET with `?ok=` / `?err=` flash messages, and `audit()` writes to the mod log. The panel is off (and serves a 503 explanation) until `DISCORD_CLIENT_SECRET` and `PUBLIC_URL` are set. The **Overview** (`overview-page.ts`) is the health page: stat cards (bot, background jobs, world state with `worldStateLine` from status.ts, members, next event, latest backup), the jobs table from `jobs.stats()`, the World State boards from `feedHealth()` (channel, last round, an error, "kept" when the world state could not be read, "near the limit" above 85% of Discord's 4000 characters or 40 components; details go on a full-width line under the row), and where every feature posts. `CHANNEL_SETTINGS` (same file) is the one list of channel settings, shared by that Overview section and the **Settings** page's channel form, which saves only the fields the form sent (a page opened before an update never clears a setting it did not show), checks each channel or role still exists, runs `assertChannelFree` for the chat channel, calls `skipCurrentWeek` when the weekly channel changes (like `/setup weekly`) and audits what changed. `test/admin.test.ts` drives it over HTTP with a stub client.

**Look and feel** (`src/web/theme.ts`, `src/discord/style.ts`): one design system per surface, so a new page or embed looks like the rest by default. `theme.ts` is the CSS for both web surfaces (tokens, base, components, then `ADMIN_CSS` and `STATUS_CSS`): dark, the logo's crystal blue as the accent, no inline `style=` attributes and no `data:` images (the CSP forbids both; use a class such as `.mt`). The admin layout (`pages.ts`) is a sidebar with grouped navigation (Server / Tools / System) and a top bar; every page starts with `head(title, lede)` and builds on `statCard`, `badge`, `actionButton` and the `card`/`stack`/`row`/`grid` classes (`.inline` forms keep their "sure" checkbox next to the button). The signed-out pages are a centred card (`.solo`).

**Runtime config** (`src/runtime-config.ts`, the panel's **Config** page `src/web/admin/config-page.ts`): the settings in `SETTINGS` (world state on/off/URL/interval, platform, clan and bot name, Ollama URL/model/timeout, free cloud endpoint/models/limit (the screenshot readers), SearXNG URL, the queue, and the restart-only flags ENABLE_MESSAGE_CONTENT, ENABLE_MEMBER_LOGGING, ENABLE_WELCOME and WIKI_INDEX) can be changed without a redeploy. A panel value is stored in `bot_meta` as `cfg_<NAME>` = `v:<text>` (`v:` with nothing = explicitly off), validated with the same zod schema as the environment, and applied by writing into the shared `config` object, so every `ctx.config.X` read sees it at once; `initRuntimeConfig` (in `index.ts`, right after the store exists and before the client reads the intents) applies stored values on top of the environment at every start, `onSettingChange` re-configures the world state client and refreshes the bot name, and settings with `restart: true` show a restart banner and button (`scheduleRestart`). Precedence: panel value, then environment, then built-in default; "reset" removes the panel value; "Copy the current environment values into the panel" pins every env-set value so the variables can be dropped from the stack. Deliberately **not** covered (`ENV_ONLY`): secrets and tokens, DISCORD_GUILD_ID, DATA_DIR, HTTP_HOST/PORT, PUBLIC_URL and PANEL_OWNER_IDS (the panel login), MCP_ALLOWED_HOSTS and WATCHTOWER_URL. A new overridable setting is one entry in `SETTINGS`. `test/runtime-config.test.ts`.
