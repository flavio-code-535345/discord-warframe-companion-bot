# Riven analyzer

Notes for this folder. The rules that apply everywhere, the commands and the list of the other notes are in the root `CLAUDE.md`.

**Riven analyzer** (`src/rivens/`, `/riven grade|scan|find|watch|top|status`, MCP `grade_riven`, `find_rivens`, `riven_top_rolls`, `riven_status`; Config page group "Riven analyzer": `RIVEN_CRAWL_ENABLED`, `RIVEN_CRAWL_INTERVAL_SECONDS` 45, `RIVEN_REFRESH_DAYS` 3, `RIVEN_HIGH_PRICE` 1000): grades a riven by **how common its rolls are among the expensive listings on warframe.market** (the clan co-owner's idea) and shows what similar rolls are listed for (asking prices, not sales). AlecaFrame was checked and does not help here: its riven analyzer is an in-game overlay, and its public API only has stats (plat, endo, ducats, MR, trades) and relic inventory, with no riven data. Data: `market.ts` reads the weapon and stat lists from the v2 API (`/v2/riven/weapons`, `/v2/riven/attributes`; their `disposition` is obsolete, since hotfix 44.1.3 of 2026-10-22 gave every riven the same range) and the listings from **`/v1/auctions/search?type=riven&weapon_url_name=<slug>&sort_by=price_desc`** (v2 had no public auction search when this was written, and v1 was assumed to still serve it: if `/riven status` shows 403/404 errors, the endpoint moved, change `AUCTIONS_URL` and the shape in `parseAuctions`, which already accepts both spellings of the bonus flag, snake and camel case). One request per weapon returns its most expensive listings (about 500); `riven_listings` keeps only price, polarity, re-rolls and the stats (never the seller) and `riven_crawl` when each weapon was read and how it went (migration 22, in bot.db). **Politeness:** every call goes through the shared `ApiClient` in its own **`rivens` scope** (`send(..., { scope })`, a separate gap and cooldown key `api.warframe.market#rivens`, so a 403/429 here pauses riven reads and never `/price`); `RivenCrawler` (the `riven-crawl` job, which waits `intervalMs` after each step) reads ONE weapon per interval as background work (half the global budget), never-read weapons first and then the oldest one that is due, leaves a failed weapon alone for 6 h, rests an hour after 3 failures in a row and sends nothing while the scope is blocked. A person asking for a grade never triggers a crawl: `loadListings` uses stored listings younger than 6 h, else makes one read for that weapon (shared by simultaneous askers), falls back to older stored ones if warframe.market can't be read, and only then fails with a `UserError`. **Grading** (`grade.ts`, pure): the high bracket is the listings at or above `RIVEN_HIGH_PRICE`, or the weapon's top quarter (at least 8) when fewer reach it, and a weapon with under 16 listings gets no grade; the letter comes from where each bonus stat ranks among the bracket's most common bonus stats (top 3 = 2 points, top 6 = 1), S only when the exact combination also exists among the expensive ones; the embed also shows each stat's share, the value percentile among listed rolls (when a value was typed), the curse's share, and the asking prices of listings with the same bonuses (same curse when 3+ exist). **Prices come from a second, filtered request, not from the stored listings**, because one request only returns a weapon's 100 priciest, so anything computed from them leans high: `fetchComparable` asks `positive_stats=<slugs>&negative_stats=<slug>&sort_by=price_asc&buyout_policy=direct` when someone grades (user-facing, cached 30 min, never stored), keeps only listings that really carry exactly the graded bonuses, and `complete` means fewer than a page (100) came back, i.e. that is everything for sale (count, range and median are right); otherwise only the cheapest and 10th cheapest are shown. If the market refuses the filtered search with 400/422 it is not tried again for 6 h, and any failure falls back to the stored priciest listings, which the embed labels as such (`source: 'top'`); the value percentile is likewise only among those priciest listings. The filter parameter names come from the old v1 API docs and were not verified against the live API: if grades always show the "priciest listings" wording, the filter is being refused. Stat input (`stats.ts`) takes names or short forms (`cc cd ms sc dmg fr`...) with optional values. `test/rivens.test.ts` uses a fake warframe.market. **Riven channel** (`/setup rivens channel:` / `/setup off feature:Riven scanning`, setting `rivenChannelId`, migration 23; `src/rivens/channel.ts`): members post riven screenshots and Ordis answers each message with ONE short card, no explanations (the owner asked for "just grade"): `rivenCompactEmbed` / `scanSummary` in `riven-embeds.ts` give weapon, big letter, the stats as read and the price range, or a single `❌` line when the picture can't be read (`/riven scan` uses the same card; `/riven grade` keeps the detailed embed). `handleRivenMessage` runs in `bot.ts` after the screenshot-roles handler, ignores messages without a PNG/JPEG (up to 3 are read, one reply), never deletes or stores anything, shows progress only as a 🔎/⏳ reaction (removed afterwards), and shares `screenshotQueue` and its per-person limit. It does not need Message Content: with the intent off the gateway delivers messages with no attachments, so a message without any is re-read over REST (`message.fetch()`) and the REST copy has them (found in production: `riven_status.channel` shows what the handler saw, `messageContentOn`, and the last decisions);  the channel is excluded from leveling XP and clean stickies and is in the backup restore key list. `scanLog()`/`scanTotals()` keep the last 40 scans in memory for the admin panel's **Rivens** page (`src/web/admin/riven-page.ts`: scan channel form, counters, slow-crawl status, a screenshot test area that posts the raw image with the CSRF header to `/admin/rivens/scan`, latest scans). `test/riven-channel.test.ts`. **`/riven scan image:`** grades from a screenshot of an unveiled riven card, **with OCR only** (the same tesseract.js engine as the screenshot roles, no vision model, nothing stored): `prepare.ts` makes the picture OCR-friendly in pure JS (grayscale, light-on-dark inverted, contrast stretched, enlarged 2-3x when small), `card.ts` (`parseRivenCard`, pure) takes the weapon from the card's name (longest weapon name wins, one wrong letter forgiven in longer names) and the stat lines (a number with a % or a sign, then a name matched with `closestAttribute`, which forgives a wrong letter or two), and `scan.ts` (`scanCard`) retries on the unmodified picture when the cleaned one yields too little, then calls `gradeResolved` (the same grader as `/riven grade`). It never grades a guess silently: the reply starts with a "What I read" embed (weapon, bonuses, curse, values) plus notes for stat lines it could not match and for stats whose +/- sign OCR missed (a fourth unsigned line is taken as the curse, three unsigned lines are all taken as bonuses and flagged); Weapon Recoil is the one stat where the game's minus sign is the bonus. A card with no weapon or fewer than 2 bonuses gets an explanation instead of a grade. It joins `screenshotQueue` like the role screenshots (queue position message, 90 s limit on the reading), accepts PNG/JPEG up to 8 MB, The weapon is the words before the riven name's hyphenated word (`Zarr Crita-parciata`), matched with one wrong letter forgiven; stat names forgive stray trailing letters (`matchName`: `Damage p`, `Zoom b` from the card frame). **A stat line that looks like a stat (signed or with a decimal) but can't be matched blocks grading** (`ScanResult.problem` explains and shows what to type with `/riven grade`), because a missing stat changes the grade: a real screenshot had the mouse pointer over `Critical Chance` and OCR gave noise there, which is the fixture in `test/riven-scan.test.ts` (real tesseract output: about 0.9 s on the 3x enlarged card). `test/rivens.test.ts`, `test/riven-scan.test.ts` use a fake warframe.market and a fake reader.

**Unreadable stat lines are interpreted, not refused** (the owner: "always try to interpret what it could be"): `scanCard` first reads the cleaned picture (and the original when that is poor), then, when a stat line is unreadable, `pointer.ts` (`erasePointer`) paints a mouse pointer (a compact, taller-than-wide, colourless near-white shape, searched only in the band of the failed line so the artwork's white is never touched) out of the picture and it is read again (this recovered `Critical Chance` under the pointer in the real Zarr card), and `interpretUnknown` (`card.ts`) works out what is still unreadable from the line's value and sign, the stats the card does not already have (a minus can't be a positive-only stat) and the best fit between what is left of the name in EVERY OCR reading and each stat name (a small bonus for common stats breaks ties). The result is graded and the stat shows with a `?` on the compact card (`CardReading.guessed`). Stat lines are only read between the riven's name and the `MR` footer, so noise in the artwork never counts. `test/riven-scan.test.ts` (pointer, interpretation), `test/riven-channel.test.ts`.

**Misreads are corrected against the ranges** (found with real cards from the clan): a stat name can wrap onto a second line ("Critical Chance" / "for Slide Attack", with the "(x2 for Heavy Attacks)" note between), which `card.ts` joins (`nameWithContinuation`: the joined text only wins when it is a longer name that starts with the first line, so a noise line changes nothing); and OCR can lose a "+" ("d 195.2%" for "+95.2%"). When the values fit no range (`fitsTable`), `scanCard` reads the picture as it came as a second opinion and `repairValues` (rolls.ts) tries, per stat, what the other readings gave and then the value with one digit left out, accepting the fewest changes after which EVERY stat fits (a game range is only 90%-110%, so a false repair is very unlikely); the corrected values are what the picture shows. The grades were checked against a third-party riven tool's numbers for the same riven (Nukor Sati-plagaata: C-, B+, C, B) and match. `riven_table_check` (MCP) grades all stored listings against the table per kind of weapon (fit rate, stats without a range, where each stat's rolls sit in its range).

**The answer to a scan is a picture** (`picture.ts`, `reply.ts`; `rolls.ts`): the owner asked for the look of an overlay tool: the card on the left and, on the right, the weapon name and one block per stat, `+101.3% Heat:` then `Grade:  A+  (+9.159%)` in a colour from green to red, **a grade for every roll, not for the riven as a whole**. A stat's value is random within 90%-110% of an average that depends on the weapon, the stat and the number of bonuses/curses; the percentage is where the roll sits in that range (+10 is the best possible roll) and for a curse a milder value is the better one. The average comes from the wiki's fixed ranges (`ranges.ts`, generated from the Riven Mods page: a base value per stat and kind of weapon (rifle, shotgun, pistol, archgun, melee) times a disposition times the layout weight, `WEIGHTS`: 2 bonuses 0.99, 2+curse 1.2375/0.495, 3 bonuses 0.75, 3+curse 0.9375/0.75). `gradeByTable` (rolls.ts) tries each kind of weapon (the market's `rivenType` first when its list gives one, else rifle, pistol, shotgun, archgun, melee) with the weapon's own disposition (old rivens were rolled with it; the reference card is a pistol-type Arca Scisco at 1.1 and reproduces to 0.1%) and the wiki's current constant 1.2, and takes the first combination in which EVERY stat of the card falls inside its 90%-110% window (so a rifle's damage range is not mistaken for a pistol's). Only when nothing fits (an unknown stat, or a roll from another version of the game) does it fall back to the old estimate from the stored market listings: dividing each listing's value by the layout weight, taking the largest as 110% of the average (which leans on old rivens rolled with other dispositions) and needing `MIN_SAMPLES` (8) listings, else the stat shows `not enough data`. `statKey` maps the wiki's, the market's and the slugs' spellings of a stat to one key. `riven_status` shows what the market's weapon list gives (`weaponList`: kinds, dispositions) and what the channel handler saw. Letters from `letterFor` (A+ from +8 down to C- and D). `GradeReport.rolls` carries them. `picture.ts` draws with pureimage (pure JS, no native canvas) and Roboto from `@fontsource/roboto`: pureimage reads TTF only, so `imaging/font.ts` converts the packaged WOFF to TTF at start (`woffToSfnt`, written to the temp dir) and registers regular and bold as two families. A big screenshot is cropped to the card from the OCR'd text block (`cardCrop`, `CardReading.box`, `Prepared.sourceScale`). `rivenReply` returns the picture as a file, or the short text card when nothing can be drawn (unreadable card, no data) or drawing fails; the riven channel and `/riven scan` both use it through `rivenReplies` (one picture per image in a single reply). Under the stats the picture has a footer: the weapon's most wanted bonus stats (`Grade.wanted`, the three most common among its expensive listings; green when this riven has them), what rivens with these bonuses are listed for (`saleText`, from the filtered search) and what the rolls were measured against (`basisText` from `GradeReport.basis`: the kind of weapon and its disposition, today's ×1.2 range, or the listed rolls). `test/riven-rolls.test.ts`, `test/riven-find.test.ts`.

**Reroll comparison, find and watch** (`compare.ts`, `find.ts`, `watch.ts`; `test/riven-find.test.ts`): two or three screenshots of one weapon's rivens in one message (the riven channel) or `/riven scan image: compare:` are numbered `#1`, `#2` on their pictures and `compareRivens` says which to keep as the message text: the market letter first (whether expensive rivens carry those bonuses), then the average roll deviation (`rollScore`; within 1% it is "Either one"). `/riven find weapon bonuses [curse] [max_price] [in_game]` (and MCP `find_rivens`) lists the cheapest matching rivens for sale: `resolveFilter` (1-3 bonuses, a curse or "none"), one `fetchComparable` search (fixed buyout prices, cached 5 min), `matchesFilter` (the market returns supersets: every wanted bonus, maybe one more; the curse rule; the price), `complete` when the answer was under a page or already went past the price limit. Each listing (`listingLines` in riven-embeds.ts) links its auction page (`auctionUrl`, where the seller's name and whisper are) with the seller's status (in game/online/offline), MR, re-rolls, polarity emoji and the stats in the game's notation (`formatStatValue`: `+90.2%`, `x0.59` for faction stats, `+8.5s` combo duration, from the attribute list's `unit`); `parseAuctions` reads those extra fields but the database never stores them. `/riven watch weapon bonuses max_price [curse]` (ephemeral; at most `MAX_RIVEN_WATCHES` 3 per member, within `MAX_TRACKERS_PER_USER`) is a tracker of kind `riven`: the command searches once, shows what is already for sale and records it (`noteMatches`), and the `riven-watch` job (every 5 min, `checkRivenWatches`) searches per weapon/bonuses/curse group (watches that differ only in price or the no-curse rule share one request), at most 6 groups a round, longest-waiting first, as background work in the `rivens` scope; each new match is DM'd once (`rivenDm`, a card with up to 5 listings and a link to the market's search, `searchPageUrl`), de-duplicated with `seen_worldstate` keys `riven:<trackerId>:<auctionId>` that `refreshSeen` keeps fresh while the riven stays listed (so a price drop below the limit is news, and a still-listed riven is never sent twice); a watch that never got to look first records silently (`riven_watch_seeded:<trackerId>`). A full request budget or a market cooldown just ends the round; another failure ends it and fails the job.
